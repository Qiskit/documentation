Manage a quantum-centric supercomputing workflow with QCSC-Prefect

Usage estimate: 30 seconds of QPU time on an IBM Quantum® Heron r2 processor. This estimate excludes queue time and classical processing. Your runtime might vary.

Learning outcomes

  • Trace a quantum-centric supercomputing (QCSC) workflow in Prefect Cloud, with one task per Qiskit pattern stage.
  • Configure the workflow by role, with run parameters in the Prefect Cloud run form and the high-performance computing (HPC) and quantum processing unit (QPU) settings in Prefect blocks.
  • Resume a failed run without repeating its QPU job, and reuse the samples of one run in a new run.

Prerequisites

  • Set up QCSC-Prefect on a Slurm cluster, which prepares the Slurm login node, the Python environments, and the IBM Quantum credentials.
  • Sample-based quantum diagonalization of a chemistry Hamiltonian, which explains the algorithm.

Background

A QCSC workflow runs a QPU and an HPC system as one machine. QCSC-Prefect runs QCSC workflows on Prefect and keeps them traceable, configurable, and resumable.

This tutorial demonstrates these features with sample-based quantum diagonalization (SQD) of the N2_22​ molecule. The Quantum Resource Management Interface (QRMI) samples the circuit inside a Slurm job. The Fulqrum eigensolver diagonalizes the sampled subspaces in more Slurm jobs. One Prefect Cloud deployment runs both.

QCSC-Prefect also runs large QCSC workloads, as in the following projects.

  • A study of protein-ligand complexes with more than 12,000 atoms used QCSC-Prefect. It sampled quantum-embedding fragments on two 156-qubit IBM Quantum processors, with up to 94 qubits, and diagonalized the fragment subspaces on the Fugaku, Miyabi-G, and ROQUO supercomputers [1].
  • A study of iron-sulfur clusters ran an extended QCSC-Prefect SQD workflow with 36 orbitals (72 qubits) and subspace dimensions up to 3×10103 \times 10^{10}3×1010 on the Fugaku, Miyabi, and ROQUO supercomputers [2].

The challenge of QCSC workflows

The SQD workflow is typical of QCSC workloads. QCSC-Prefect answers each of its challenges with one feature, as in the following table.

Challenge
QCSC-Prefect feature
It spans several resources. A Slurm job holds the QPU, then many Slurm jobs diagonalize subspaces, round after round.Traceable workflow
It has many parameters at different levels (science, circuit, and cluster), and credentials must stay out of all of them.Configurable parameters
It is long and can fail anywhere, from a walltime limit, a node failure, or a long QPU queue. Without care, a late failure means sampling on the QPU again.Resumable execution

Traceable workflow

A Prefect flow is a Python function made of tasks. QCSC-Prefect makes each stage of a Qiskit pattern (Map, Optimize, Execute, and Postprocess) one task. For every run, Prefect Cloud shows the following information:

  • The task graph, with an arrow wherever one task passes its result to another.
  • The state, inputs, logs, and duration of each task, filterable by the stage tags map, optimize, execute, and post-process.
  • The artifacts, which are tables and links that tasks publish, such as the source of the samples or the energy of each subspace.

The workflow host only submits and monitors work. The compute-intensive work runs as Slurm jobs, as in the following image.

Resumable execution

Prefect stores the results of the first three stages with the flow run. If a later task fails, Retry on the flow run reuses the stored results and runs only what failed, as in the following image.

A new run can also load the samples of an earlier run instead of sampling, because the Execute stage records where its samples are.

SQD at a glance

SQD samples bitstrings from a local unitary cluster Jastrow (LUCJ) circuit built from coupled cluster singles and doubles (CCSD) amplitudes, fixes the bitstrings that noise has corrupted (configuration recovery), and diagonalizes the Hamiltonian in subspaces spanned by the sampled configurations [3]. The SQD tutorial explains the algorithm. In QCSC-Prefect, SQD is the flow sqd, which has the following task graph.

Stage
Task
Input from another task
Mapcompute_molecular_integralsNone
Optimizeget_lucj_paramsIntegrals from Map
Executequantum_sampling, with build_lucj_circuit inside itLUCJ parameters from Optimize
Postprocesssqd_loopIntegrals from Map, and samples from Execute

When a run reuses samples, load_qrmi_result (or load_runtime_job for samples from IBM Quantum Platform) replaces both get_lucj_params and quantum_sampling, so the run has no Optimize task. In random mode (Quantum Source set to random), there is no Optimize or Execute task, and Map feeds sqd_loop directly.

The example is N2_22​ at a bond length of 1.1 A˚\AAA˚ in the 6-31G basis, with the two 1s core orbitals frozen. This leaves 16 spatial orbitals with five α\alphaα and five β\betaβ electrons, which is a 32-qubit circuit.

Keep the following points in mind when you edit the file.

  • Write the paths out, because the file does not expand environment variables. The ~ character works. Keep every top-level key, such as python_executable, before the first table header.
  • The [qrmi] table needs no change, because the qrmi-runtime block supplies the instance and the QPU. Set resource only to override the backend. The credentials stay in qrmi_config.json, not in this file.
  • The slurm profile holds the scheduler and resource settings of a generic Slurm cluster, and any key in your file overrides it. The commented [sqd_advanced] table sets the sqd-advanced-settings block, the commented [advanced] table sets block names and timeouts, and the table of each solver holds its tuning. To choose the nodes, ranks, and threads of the solver jobs, see Size the SQD diagonalization for your HPC resources.
  • The QRMI job and each solver job have a walltime of 12 hours (#SBATCH --time), and the flow waits up to 13 hours (timeout_seconds = 46800) for each job. To change the walltime, set walltime at the top of the file for the solver jobs, or in the [qrmi] table for the QRMI job, for example walltime = "02:00:00". A shorter walltime can start sooner on a busy cluster.

Qiskit Pattern in QCSC-Prefect step by step

The following steps compute the four stages in this notebook with PySCF, ffsim, Qiskit, Qiskit Runtime, and qiskit-addon-sqd, without Prefect. See the SQD tutorial for the details of each computation.

Step 1: Map classical inputs to a quantum problem

The Map stage, the task compute_molecular_integrals in the workflow, turns the molecule into the inputs of all later stages. Restricted Hartree-Fock (RHF) gives the molecular orbitals, and the active-space integrals leave out the two frozen 1s cores. CCSD gives the t2t_2t2​ amplitudes of the ansatz, and its density matrix gives the orbital occupancies that start configuration recovery. CCSD iterates CCSD_MAXITER times, each time from the previous amplitudes, so the result does not depend on the DIIS history of the first iteration. This notebook uses 4 iterations, and the workflow uses 10.

ATOM = "N 0 0 0; N 0 0 1.1"
BASIS = "6-31g"
N_FROZEN = 2
CCSD_MAXITER = 4

mol = pyscf.gto.M(atom=ATOM, basis=BASIS, symmetry=False, verbose=0)
mf = scf.RHF(mol).run()
norb = mol.nao_nr() - N_FROZEN
nelec = (mol.nelec[0] - N_FROZEN, mol.nelec[1] - N_FROZEN)

# Active-space Hamiltonian with the 1s cores frozen
cas = mcscf.CASCI(mf, ncas=norb, nelecas=nelec)
one_body_tensor, core_energy = cas.get_h1eff()
two_body_tensor = ao2mo.restore(1, cas.get_h2eff(), norb)

# CCSD, iterated from the previous amplitudes
ccsd = cc.CCSD(mf, frozen=N_FROZEN)
eris = ccsd.ao2mo()
ccsd.kernel(eris=eris)
for _ in range(CCSD_MAXITER - 1):
    ccsd.kernel(ccsd.t1, ccsd.t2, eris=eris)
t2 = ccsd.t2

occupancies = np.diag(ccsd.make_rdm1())[N_FROZEN:] / 2
initial_occupancies = (occupancies, occupancies)

print(f"norb = {norb}, nelec = {nelec}")
print(f"E(RHF)  = {mf.e_tot:.8f} Ha")
print(f"E(CCSD) = {ccsd.e_tot:.8f} Ha")

Output:

norb = 16, nelec = (5, 5)
E(RHF)  = -108.86761837 Ha
E(CCSD) = -109.09392115 Ha
How QCSC-Prefect manages this step

Trace: The task compute_molecular_integrals has the tag map. Its result goes to get_lucj_params and sqd_loop, so two arrows leave it in the graph. The task logs show the PySCF output.

Configure: The Molecule group of the run form selects the problem, as an FCIDUMP file or as a geometry and basis. This workflow reads algorithms/open_loop/sqd/data/n2_631g_fc.fcidump, which has the cores frozen already. The number of CCSD iterations (CCSD Restarts, 10 by default) is in the sqd-advanced-settings block.

Resume: The result is persisted (compressed/json), so Retry loads it instead of running PySCF again.

Step 2: Optimize problem for quantum hardware execution

The Optimize stage, the task get_lucj_params in the workflow, fits the ansatz to the QPU before any circuit exists. ffsim builds the LUCJ operator from t2t_2t2​ with only the interactions that a heavy-hex lattice runs without SWAP gates. These are the same-spin pairs of neighboring orbitals and the opposite-spin pairs on every fourth orbital, at most five on a heavy-hex (Heron) processor. ffsim then compresses the operator (optimize=True, on by default in the workflow) so that one layer reproduces t2t_2t2​ more closely.

N_REPS = 1

pairs_aa = [(p, p + 1) for p in range(norb - 1)]
pairs_ab = [(p, p) for p in range(0, norb, 4)][:5]

lucj_op = ffsim.UCJOpSpinBalanced.from_t_amplitudes(
    t2,
    n_reps=N_REPS,
    interaction_pairs=(pairs_aa, pairs_ab),
    optimize=True,
    options={"maxiter": 50},
)
n_params = ffsim.UCJOpSpinBalanced.n_params(
    norb, N_REPS, interaction_pairs=(pairs_aa, pairs_ab)
)

print(f"Opposite-spin pairs: {pairs_ab}")
print(f"Ansatz parameters: {n_params}")

Output:

Opposite-spin pairs: [(0, 0), (4, 4), (8, 8), (12, 12)]
Ansatz parameters: 275
How QCSC-Prefect manages this step

Trace: The task get_lucj_params has the tag optimize. Its result carries everything that the circuit needs, so one arrow leads from it to quantum_sampling.

Configure: The Circuit group of the run form sets the LUCJ layers, the compression and its iteration limit, and the QPU Topology (heavy-hex or square), which sets the interaction pairs. The sqd-advanced-settings block holds reset mitigation and the transpiler settings (the optimization level and the SABRE layout search) that the Execute stage uses.

Resume: The result is persisted (compressed/pickle), so a long compression runs only one time, even if you retry the run.

Step 3: Execute using Qiskit primitives

The Execute stage, the task quantum_sampling in the workflow, builds the circuit (Hartree-Fock state, LUCJ operator, and measurement), transpiles it for the QPU, and samples it. The ffsim PRE_INIT passes run first in the transpiler and turn the ffsim gates into efficient native-gate sequences. This notebook samples with Qiskit Runtime on ibm_fez. Replace ibm_fez with a backend that your instance can use. The workflow samples with QRMI instead, in a Slurm job that holds the QPU.

service = QiskitRuntimeService()
backend = service.backend("ibm_fez")

qreg = QuantumRegister(2 * norb, name="q")
circuit = QuantumCircuit(qreg, ClassicalRegister(2 * norb, name="meas"))
circuit.append(ffsim.qiskit.PrepareHartreeFockJW(norb, nelec), qreg)
circuit.append(ffsim.qiskit.UCJOpSpinBalancedJW(lucj_op), qreg)
circuit.measure(qreg, circuit.cregs[0])

pass_manager = generate_preset_pass_manager(
    optimization_level=3, target=backend.target, seed_transpiler=24
)
pass_manager.pre_init = ffsim.qiskit.PRE_INIT
isa_circuit = pass_manager.run(circuit)
print(f"Backend: {backend.name}, ISA circuit depth: {isa_circuit.depth()}")

Output:

random_bool_array = generate_bit_array_uniform(

def correct_electron_fraction(bool_array):
    """Fraction of the bitstrings with the correct numbers of alpha and beta electrons."""
    # The right half of each bitstring is alpha, the left half is beta.
    n_alpha, n_beta = nelec
    valid = (bool_array[:, norb:].sum(axis=1) == n_alpha) & (
        bool_array[:, :norb].sum(axis=1) == n_beta
    )
    return valid.mean()

How QCSC-Prefect manages this step

Trace: The task quantum_sampling has the tag execute, and the task build_lucj_circuit runs inside it. The workflow host prepares the circuit and submits a Slurm job that requests the QPU. On the compute node, the SPANK plugin opens the QPU session, and the QRMI worker transpiles and samples the circuit. The task logs show the walltime of the Slurm job, the two-qubit depth of the transpiled circuit, and, when sampling completes, the IBM Quantum job ID and the QPU execution time.

Configure: The Sampling group of the run form sets the shots and the source of the samples, which is the qrmi-runtime block, the job of an earlier run, or random bitstrings. The QRMI blocks hold where and how the sampler job runs, and the credentials stay on the cluster.

Resume: The samples are persisted (compressed/pickle), so Retry submits no new QPU job. The sqd-sampling-source artifact records where the samples are, so a new run can reuse them, as in Optional: resume and reuse the workflow.

Why Execute builds and transpiles the circuit

The QRMI worker transpiles the circuit on the compute node against the current Target of the QPU, so the QRMI Runtime owns transpilation. This split prepares for fault-tolerant QCSC systems, where the transpilation of quantum low-density parity-check (LDPC) error-correction circuits is a heavy workload. The workflow caches the circuit parameters, not the circuits. Map and Optimize design the circuit. Map computes the CCSD amplitudes, and Optimize compresses the LUCJ operator with ffsim.UCJOpSpinBalanced.from_t_amplitudes(optimize=True), which can take longer than the transpilation for a current QPU. build_lucj_circuit and the transpiler only encode these parameters into an ISA circuit. This split differs from the conventional Qiskit pattern, and it suggests what a Qiskit pattern can look like in a QCSC system.

Step 4: Postprocess and return result in desired classical format

The Postprocess stage, the task sqd_loop in the workflow, runs self-consistent configuration recovery. Each round corrects the sampled bitstrings with the current orbital occupancies, diagonalizes the Hamiltonian in several batches of configurations, and updates the occupancies from the best result. The following cell runs diagonalize_fermionic_hamiltonian on both sample sets with the same settings. The subspace dimension is the workflow's 1,000,000 determinants (1,000 strings per spin). The notebook uses two batches per round and ten rounds, and the workflow uses four batches and five rounds. As in the workflow, Fulqrum diagonalizes each subspace. sci_solver_from_integrals builds the Fulqrum Hamiltonian one time and returns the sci_solver that the function calls for each batch. A TrimPolicy, as in the SQD tutorial, merges the heaviest strings of the batches into one subspace and diagonalizes it. Of the strings above carryover_threshold, the policy keeps the heaviest half (carryover_ratio=0.5) for the next round, like the workflow's Carryover Fraction.

SUBSPACE_DIM = 1_000_000
NUM_BATCHES = 2
MAX_ITERATIONS = 10

policy = TrimPolicy(
    trim_ratio=0.8,
    carryover_threshold=1e-4,
    carryover_ratio=0.5,
)
sci_solver = sci_solver_from_integrals(one_body_tensor, two_body_tensor)


def run_sqd(bool_array, label):
    """Run SQD on the samples, and return the final energy and the energy of each round."""
    round_energies = []

    def callback(results):
        round_energies.append(
            min(result.energy for result in results) + core_energy
        )
        print(
            f"{label}, round {len(round_energies)}: {round_energies[-1]:.8f} Ha"
        )

    result = diagonalize_fermionic_hamiltonian(
        one_body_tensor,
        two_body_tensor,
        bool_array,
        samples_per_batch=1000,
        norb=norb,
        nelec=nelec,
        num_batches=NUM_BATCHES,
        max_iterations=MAX_ITERATIONS,
        policy=policy,
        sci_solver=sci_solver,
        symmetrize_spin=True,
        max_dim=int(np.sqrt(SUBSPACE_DIM)),
        initial_occupancies=initial_occupancies,
        callback=callback,
        seed=np.random.default_rng(24),
    )
    return result.energy + core_energy, round_energies


quantum_energy, quantum_round_energies = run_sqd(
    quantum_bool_array, "Quantum samples"
)
random_energy, random_round_energies = run_sqd(
    random_bool_array, "Random samples"
)
print(f"SQD energy with quantum samples: {quantum_energy:.8f} Ha")
print(f"SQD energy with random samples:  {random_energy:.8f} Ha")

How QCSC-Prefect manages this step

Trace: The task sqd_loop has the tag post-process. It receives the samples and the integrals, so the graph shows two arrows into it. Each batch is one FulqrumSolverJob call, a solve_eigenstate task that submits one Slurm job running Fulqrum. The batches of a round run concurrently on the compute nodes. The sqd-configuration-recovery artifact lists the energy and dimension of every subspace in every round.

Configure: The SQD group of the run form sets the subspace dimension, the number of batches, and the number of rounds. Solver Block Override (solver_block_ref) in the run form replaces the Solver Block of sqd-advanced-settings for one run, for example with a DICE or SBD block. The eigensolver (PRIMME), threads, and walltime are in the sqd-fulqrum-solver block and its execution profile. The flow loads the solver block before any stage, so a wrong block name fails the run before it uses the QPU.

Resume: sqd_loop is not cached, but it saves a checkpoint after every round, in sqd_checkpoints/<flow run id>/ckpt_t00_w0.npz under the solver's work_dir. The checkpoint holds the occupancies that seed the next round and the best energy so far. On Retry, sqd_loop continues after the last completed round, with the current blocks.

Optional: resume and reuse the workflow

Retry a failed run, and reuse its samples

Retry: Suppose that, in a run with Max Iteration set to 10, a solver job hits its walltime in round 5 and sqd_loop fails. Raise the walltime in the exec-sqd-fulqrum-slurm block under Blocks, then select Retry on the failed flow run. The retried run loads the stored results of the first three stages and submits no QPU job. It runs only sqd_loop again, with the new walltime, and starts at round 5 from the checkpoint of round 4. Its log shows [ckpt] RESUME from …: completed 4 step(s), then SQD iteration 5/10, as in the following image.

Reuse: A new run computes everything again unless you point it to earlier samples. To try another subspace dimension with the same samples, start a custom run with the same parameters, set Load from QRMI Job Directory (qrmi_result_dir) to the work directory in the sqd-sampling-source artifact of the first run, and change Subspace Dimension. The new run replaces get_lucj_params and quantum_sampling with load_qrmi_result, which reads the samples and submits nothing to the QPU. Reset Mitigation in sqd-advanced-settings must match the first run, because the reload applies it. For samples taken through IQP, set Load from Qiskit Runtime Job ID (qiskit_runtime_job_id) instead, and the stage is load_runtime_job. It reads the job with the credentials of the prefect-qiskit QuantumRuntime block named in Quantum Runtime Block (reload) (ibm-runner by default). Create that block one time with prefect block create quantum-runtime.

Continue a recovery with more rounds: Start a custom run with the same parameters, set Resume from Checkpoint (resume_checkpoint) to the path in the sqd-checkpoint artifact of the first run, and raise Max Iteration. The new run continues after the completed rounds, from the stored occupancies and best energy. For example, a checkpoint with 32 of 100 rounds done and Max Iteration set to 200 continues at round 33/200. The new run reads that checkpoint and writes its own, and the following rules apply.

  • The samples, the molecule, Subspace Dimension, Batch Number, and the solver type (the fulqrum_solver_job part of the solver block) must match the first run, so reuse its samples as in Reuse.
  • The name and the job settings of the solver block, such as its walltime, can change.
  • If a setting that must match differs, the run fails before any solver job and names the difference.
