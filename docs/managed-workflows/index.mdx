# Introduction to managed workflows

<Admonition type="info" title="Plan availability">
IBM Quantum Functions and managed workflows are beta features available only to Premium, Flex, and On-Prem (via IBM Quantum Platform API) plan users.
</Admonition>

Managed workflows run your custom Python code on classical compute that IBM Quantum&reg; Platform manages for you. Use managed workflows to run hybrid quantum-classical workflows, large-scale diagonalization, and long-running parallel tasks without managing compute infrastructure or storage.

Use a managed workflow when no [pre-built Catalog Function](/docs/guides/compute-services#functions) covers your task, or when you want to package your own method as a reusable function:

- **Run long jobs in the cloud.** A managed workflow keeps running when you close your laptop, and you can reconnect to the job later.
- **Use large-memory and GPU nodes.** Choose the memory, CPU, and GPU resources that the workload needs.
- **Run tasks in parallel.** Scale out by running many single-node jobs at the same time.
- **Share a reusable program.** Upload the workflow once, and collaborators in your instance can reuse it. *NOTE: check for launch.*

You provide the workflow code, its dependencies, and the compute sizes that it supports. Functions runs the workflow on IBM-managed compute in a pre-built environment with your packages installed, and provides cloud storage for the files that the workflow reads and writes.

## How managed workflows work

You upload a workflow once and run it as many times as you need. Each run is a job. Every job works in the following ways:

- The job starts in a new environment with an empty local disk. Functions shuts down the environment after the job ends.
- The job runs on one of the compute sizes that you define when you upload the workflow. You can choose a different size for each run.
- The job can read and write the workflow's file storage. Files in file storage remain after the job ends.

### Lifecycle of a run

Each job runs asynchronously for up to 24 hours. You can run up to 50 jobs at the same time if your instance has enough allocation.

| Stage | What happens | Job status |
|---|---|---|
| Upload | You upload the workflow's code, dependencies, and sizes. Functions rejects an invalid upload before any job runs. | None (no job yet) |
| Queue | You call `run()`. Functions checks whether your instance has enough allocation, and schedules the job when compute is available. | `QUEUED` |
| Start | Functions creates an environment with the compute profile that you selected. | `INITIALIZING` |
| Run | Your workflow's entrypoint runs. The entrypoint can report its progress with `update_status()`, and you can read its logs with `logs()` while it runs. | `RUNNING`, or a stage that you set, such as `RUNNING: WAITING_FOR_QPU` |
| Result | The job ends, and Functions shuts down its environment. Functions keeps the result and logs. | `DONE`, `ERROR`, or `CANCELED` |

### What a running job can access

![You call run() with arguments from your Python session and receive status, logs, and the result. Inside the managed workflow, each run executes in an isolated job environment for up to 24 hours, with access to your workflow code and packages, its arguments, and compute. The job produces outputs with save_result(), logs(), and update_status(). Both its classical compute (CPU, RAM, and optionally GPU) and the QPU jobs that your code submits rely on your instance, which provides access and cost management. File storage and your instance are shared across all managed workflow jobs and persist after the job ends. The job has no internet access.](/docs/images/guides/managed-workflows/architecture.svg)

| Resource | What the job can use |
|---|---|
| **Compute** | The CPU, memory, and GPUs of the [compute profile](/docs/managed-workflows/managed-workflow-compute-profiles) that you selected for the job. |
| **Code and packages** | The files that you uploaded with the workflow, and the supported packages that are installed in the environment. |
| **Arguments** | The arguments that you passed to `run()`. Read them with `get_arguments()`. |
| **QPU access** | The credentials and instance that you used to call `run()`. QPU jobs that the workflow submits run on your instance and count against your usage. |
| **Outputs** | A result that the job saves with `save_result()`, logs that the job prints, and status updates that the job sets with `update_status()`. |
| **File storage** | [Files](/docs/managed-workflows/manage-files-across-managed-workflows) that all of your runs of the workflow share. Files remain in storage after the job ends. |
| **Internet** | No access. A job cannot make outbound connections. Declare packages when you upload the workflow, and provide data as arguments or files. |

### Security and isolation

Functions isolates each job from other jobs and limits the privileges of the code that runs in it. The access boundaries in the preceding table are part of this isolation. Functions also applies the following protections:

- **Job isolation.** No other job runs in your job's environment. This includes other users' jobs and your own jobs that run at the same time.
- **Results, logs, storage.** Only the user who ran a job can read its results and logs. *Note: check how this works with instance / user permission model*
- **Credentials.** Functions encrypts the credentials that a job uses, including your API token, when it stores them. Your workflow code can read these credentials while the job runs.
- **Privileges.** Functions removes administrator-level privileges from the environment before your entrypoint starts.

## Compare with on-premises HPC

Managed workflows differ from an on-premises HPC cluster in how you get compute time, set up software, and submit jobs. The following table compares common tasks.

{/* REVIEW: Confirm with engineering that each job runs on a single node, including tasks started with distribute_task. This affects the "Request resources" row and the "Run tasks in parallel" bullet. */}

| Task | On-premises HPC cluster | Managed workflows |
|---|---|---|
| Get compute time | Request an allocation or a reservation from the cluster administrator. | Use the allocation of your IBM Quantum instance. Functions queues each job when you call `run()`. |
| Access the system | Connect to a login node with SSH. | Use the Python client on your local computer. Managed workflows do not provide a login node. |
| Install software | Build software, load modules, or ask an administrator to install packages. | Declare packages when you upload the workflow. Each package must be on the supported list and pinned to an exact version. Functions installs the packages before any job starts. |
| Submit a job | Write a batch script and submit it to the scheduler. | Call `run()` with the job arguments. |
| Request resources | Request nodes, CPUs, memory, and GPUs. | Select one of the compute sizes that are defined for the workflow. Each job runs on a single node. |
| Run a parameter sweep | Submit a job array. | Call `run()` once for each set of arguments. |
| Store shared files | Write to a shared scratch file system. | Write to the file storage for the workflow. |
| Limit run time | Set a wall-time limit. | Functions cancels a job after 24 hours. |
| Checkpoint long jobs | Write checkpoints to scratch storage. | Save intermediate results to file storage. |
| Rerun a failed job | Resubmit the job. | Call `run()` again. Functions does not retry failed jobs automatically. |
| Monitor jobs | Check the queue and log files from the login node. | Check the status, logs, and result of each job from your local Python session. |
